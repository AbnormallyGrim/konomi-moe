# Handover

Status after the tenth session (2026-11-18). Read `README.md` for what the app does and `.trail/learnings/` for how it works and the decisions behind it.

## Done

- Python package `konomi` (src layout), managed with uv (`uv.lock`), with an `konomi` CLI: `sync`, `recommend`, `profile`, `exclude add|remove|show`, `import-offline-db`, `ui`.
- `exclusions.py`: excluded titles (plus their whole sequel chain), tags, genres, main studios and AniList custom lists, applied in ranking, discovery and offline picks.
- `app.py`: Streamlit UI. Cards are vertical keyed native containers (full-width 2:3 cover with rank badge as one `st.html` block, details below) in a CSS grid (columns at least 200px wide, filling the width, equal heights per row), styled through Streamlit's `st-key-*` classes. The Anime/Manga picker is above the tabs; Sync syncs both lists. No fit score is shown anywhere. Clicking a card opens a details dialog: description fetched on open, add to planning, exclude title and sequels, exclude labels, open on AniList. Clicking a reason chip opens an "exclude?" dialog. The sidebar holds the user, sync, options, Exclusions (review or undo, custom lists), AniList account (PIN sign-in) and offline import. Tabs: Recommendations and Your taste.
- `filters.py` and `themes.py`: filters set before a run (genres, tags, formats, years, finished, hide titles on the list (default on), hide other versions of titles the user completed, repeated or dropped in the other type), sent to AniList's search and re-checked on every candidate, plus a "main theme" judgement from ranked tags (see README). The UI has a Filters panel; cards show "Mainly …"; the details dialog shows theme strengths.
- `account.py`: AniList PIN sign-in, token file (`lab/data/anilist_token.json`, mode 600), the add-to-planning mutation (`SaveMediaListEntry`, also written to the local list copy), and descriptions.
- `pipeline.py`: one recommendation run (fit, discovery, offline picks, ranking, filling in missing covers), shared by the CLI and the UI.
- `anilist/`: rate-limited GraphQL client (30 req/min by default, honours `Retry-After` and `X-RateLimit-*`, retries 429/5xx/network errors), queries and parsing.
- `store.py`: SQLite cache of titles, lists, recommendation links, sync times and the imported offline database.
- `sync.py`: list sync in chunks of 500, then fetching only missing candidate details, plus a tag-based discovery search.
- `taste.py`: labels from scores, drops and rewatches; features; ridge model with explanations.
- `recommend.py`: candidate gathering, filtering (on list, adult, missing prequel) and ranking.
- `offline.py`: import of the anime-offline-database (`.jsonl` or `.jsonl.zst`), a rough tag-match pre-score, and fetching AniList details for the top picks only.
- 50 tests (no network, enforced by an autouse fixture in `tests/conftest.py`; the UI is tested with Streamlit's `AppTest`), ruff clean.

## Distribution plan (agreed 2026-11-17)

Separate releases on GitHub, all running locally, sharing **one web UI and one TypeScript engine**:

- **Seanime plugin:** a "For you" item in Seanime's side menu (webview `slot: "screen"` with the `sidebar: { label, icon }` option) opens a full page. MAL, Kitsu and Shikimori lists are mapped to AniList IDs. No Safari (needs Apple's $99/year account).
- **Python** stays as the lab for tuning, with an optional `uvx` command-line release.

**M2 plan (Seanime plugin), from session 8.** Facts it rests on, from the owner's Seanime clone (4bdff7b2) and live checks:
- Messaging: Seanime injects `window.webview` into the frame: `webview.send(event, payload)` goes to the plugin's `webview.channel.on(event, cb)`, and the plugin's `channel.send(event, payload)` arrives at `webview.on(event, cb)` (seanime-web/src/app/(main)/_features/plugin/webview/plugin-webviews.tsx, generateBridgeScript). It's events only, so the UI needs a small request/reply layer with IDs.
- The frame has no content security policy, and AniList answers CORS with `*` (checked live with `Origin: null`). So **the frame calls AniList's public API directly** through the engine's `fetchTransport`. Only the list, add-to-planning, storage and navigation go through the plugin. Real AniList responses do expose `X-RateLimit-Limit`, `-Remaining` and `-Reset` to browsers (`Access-Control-Expose-Headers`; only the preflight lacks them), so the client can read them in the frame. AniList's live limit was 30 a minute on 2026-11-17.
- **The list comes from Seanime**, not by username: `$anilist.getRawAnimeCollection(false)` / `getRawMangaCollection(false)` include custom lists and private lists, with no token. Entries have status, score (POINT_100), progress, repeat and updatedAt, but their media lack tags, relations and recommendations. So the engine gets `syncEntries` (store host-supplied entries, then fetch details with recommendations for list titles, then candidates), with a new `MEDIA_WITH_RECS_BY_IDS` query added to the lab and the engine together. This avoids the "anilist-token" permission (`$database.anilist.getToken` + `customQuery`).
- Add to planning: `$anilist.updateEntry(id, "PLANNING", …)`, then refresh the collection. Opening a title: `ctx.screen.navigateTo("/entry", { id })` (manga: `/manga/entry`). Storage: `$storage` ("storage" scope) holds the engine's `MemoryStore` JSON (about 2.5 MB). It's loaded once when the page opens and saved after syncs and changes.
- Manifest: `{ id, name, version, type: "plugin", language: "javascript", payload, plugin: { version: "1", permissions: { scopes: ["storage", "anilist"] } } }`. Local plugins sit in `~/Library/Application Support/Seanime/extensions/*.json` (the owner's Seanime is installed and running there).

The smoke script runs the job in a bare `vm` context; that found the missing `performance`. **Checked in the owner's real Seanime (2026-11-18):** it ran 5 s after the plugin loaded and logged "background setup done" 78 s later, after 36 AniList requests exactly 2 s apart. Ranking in goja took about 1 s, so the time is all AniList's limit: its live `X-RateLimit-Limit` was still 30 a minute, which is the client's default spacing.
- **Batched AniList requests (session 9), engine only:** AniList's limit counts requests, not what they carry, and it was still 30 a minute. So:
  - `AniListClient.queryMany` sends one query several times in a single request through GraphQL aliases (`engine/src/anilist/batch.ts`: run `i` is aliased `q<i>`, its variables suffixed `_<i>`; a single run is sent as the plain query).
  - Title fetches (`fetchMedia`, and `syncEntries`' list details with recommendations) send pages of 50, up to `PAGES_PER_REQUEST` (10) per request: 500 titles, the size of AniList's own list chunks, about 1 MB and 3–5 s per reply.
  - `discoverMany` sends searches together: a run's top-tag searches plus every filter search's first page in one request, then the remaining filter pages (2–6) of searches that still need them in a second.
  - The client takes a request's rate-limit slot before waiting, so concurrent requests still start 2 s apart while earlier ones are being answered; a back-off (429, 5xx, none remaining) holds every waiting request (`blockedUntil`). Batched fetches run their requests concurrently.
  - Measured live: 1,100 title IDs in 3 requests and 5.2 s (22 requests before); 4 searches in 1 request; a made-up 600-title list's first sync plus ranking in 6 requests and 14.6 s. The owner's real first sync had been 36 requests and 78 s.
  - Picks are unchanged: the same titles are fetched, only grouped. The one behavioural difference is that a filter search whose first page is full and passes too few now gets all its remaining pages at once, not page by page. The fake AniList answers batches run by run (`requests` lists runs, `counts.http` counts requests). The lab still fetches 50 per request; it's the tuning tool and its parity test is offline.
  - Not done: fetching only the strongest recommendations per liked title, which would cut requests further but can change picks, so it needs the evaluation harness first.
- **Search exclusions vs. the blacklist (session 9, owner request):**
  - **Bug fixed:** you could exclude a genre or tag you were filtering by, which left nothing to find. Now a filter always wins: `requiredLabels(filters)` (engine `filters.ts`) lists what the filters ask for, the run drops those from the exclusions it applies, the dialog shows them greyed out ("You're filtering by …"), `Session.excludeLabels` skips them, and Apply removes newly filtered labels from the search's exclusions.
  - **Excluding from a title's dialog now applies to that search only:** it goes into `Filters.exclude` (per type, saved with the filters) instead of the global exclusions, and shows under the filters (open or minimised) as "Excluded from this search" chips. A chip's ✕ puts the label back and ranks again right away (no list reread). Reset clears them with the other filters.
  - **Settings → Blacklisted** is the old global label list (`SavedExclusions.labels`, so earlier exclusions carry over), now with one search box over every genre, AniList tag, country and format, plus studios by name. Blacklisted choices are greyed out in the filter pickers and left out of the tag picker.
  - Everything you can filter by can be excluded: `exclusionLabels(m)` (engine `models.ts`) adds `country:` and `format:` keys to `mediaLabels`, and the dialog offers the title's format and country. Country and format exclusions are applied after fetching (AniList's search has no country-not-in), so a filter search can spend part of a page on them. Engine only; the lab's exclusions don't know these kinds.
  - Checked in headless Brave on a made-up list of public titles against live AniList: Action locked in the dialog while filtering by it, excluding Adventure showed it in the filters panel, its ✕ brought it back, blacklisting South Korea from Settings greyed it out as a filter.

## Collaborative signal experiment (session 8)

The owner asked whether other people's public ratings could make picks more accurate without hosting anything. Plan: train title vectors offline, ship only them, and fit the user's taste vector on their device.

- **Data:** Kaggle "Anime Recommendations Database" (CooperUnion), **CC0** (checked on Kaggle's own API: "CC0: Public Domain"), 73,516 MAL users, ~7.8M ratings, ending around 2016-17. Downloaded from a Hugging Face mirror whose byte count matches Kaggle's (112,341,362). It's kept outside the repo. MAL IDs map to AniList IDs through the raw offline database file (18,858 links). The lab's `offline_anime` table doesn't keep the source URLs, so the script reads `lab/data/offline-db/anime-offline-database.jsonl.zst`.
- **Method** (`lab/scripts/cf_experiment.py`): truncated SVD (64 dims) of the user × title matrix; watch-based tf-idf (implicit) beat centred scores. A fold's taste vector is the weighted, centred sum of its training titles' vectors; it's blended with the current model at a few weights. Same folds and answer key as `konomi evaluate`, over 10 seeds.
- **Results on the owner's anime list:** only 111 of 316 graded titles (35%) have a vector, because of the 2016-17 cutoff. Graded on those 111: current model AUC 0.690 ± 0.017, people-like-you alone 0.721, blend (× 2) **0.737** (hit@10 70% → 75%). On all 316 the blend adds only about +0.012 AUC and costs top-10 hit rate. So the signal is real, and coverage (fresh data) is the limit. Not adopted in the app.
- **Second run, with full coverage:** "User Animelist Dataset" (Hugging Face `mramazan/User-Animelist-Dataset`, also on Kaggle as tavuksuzdurum/user-animelist-dataset): 1.77M MAL users, 148M scores, titles into 2025. It's marked CC-BY-4.0 but collected from MyAnimeList, so it's for **private measurement only**. Every 4th user was used (341k users, 13.6k anime, 35M scores; 54 s, 4.7 GB RAM). 294 of the owner's 316 graded anime (93%) got a vector. Results on all 316, over 10 seeds:

  | | AUC | hit@10 | Spearman |
  |---|---|---|---|
  | current model | 0.705 ± 0.013 | 86% | 0.409 |
  | people-like-you alone (implicit) | 0.677 | 84% | 0.271 |
  | blend, implicit × 1 | 0.717 ± 0.013 | 89% | 0.431 |
  | blend, explicit × 0.5 | 0.709 | 92% | 0.444 |
  | blend, explicit × 1 | 0.702 | 94% | 0.441 |

  Reading: with full coverage the overall-ranking gain is small (+0.01 AUC, about one standard deviation), but the top of the list improves more (hit@10 86% → 89-94%), and the top is what users see. The 0.737 on the first dataset's 111 covered titles was optimistic (older titles, small sample). Caveats: one user, and the harness only reranks titles already on the list. It can't measure what a collaborative signal is best at, surfacing candidates the tag model would never find.
- **Cheaper ideas measured the same way** (`lab/scripts/staff_community_experiment.py`; 10 seeds, owner's lists; staff fetched once from AniList's public API for the 662 list titles, all of which have key staff):
  - **Staff as features** (one feature per person in the key roles: director, series composition, original creator or story, art, character design, music; matched across anime and manga): anime AUC **0.705 → 0.736 ± 0.010**, hit@10 86% → 89%, Spearman 0.409 → 0.460. That's better than the collaborative blend (0.717) for a fraction of the work. Half-weight staff features gain less (0.717). Manga: 0.672 → 0.686.
  - **Community weight:** anime is best near the current 0.6-1 (weight 1 with staff: 0.733, hit@10 90%, Spearman 0.482); more hurts AUC. Manga (46 labelled, 28 graded): AniList's average alone scores 0.738, and raising the weight from today's 1.96 towards 8 approaches it (5 → 0.709, 8 → 0.727) but never beats it. On a manga list this small the taste model adds nothing yet. 28 graded titles is too few to tune on with confidence.
- **Fresher sources, terms checked 2026-11-17:**
  - **Shikimori:** the terms (Russian, 2012) don't forbid collecting data; they bar copying and commercially using information that harms other users. The API docs say to use the API (GraphQL preferred) rather than parse the site, at most 5 requests a second and 90 a minute, with the OAuth app name in the User-Agent. Shikimori IDs are MAL IDs. It covers manga too.
  - **Kitsu (terms v1.0, 1 Dec 2016, pasted by the owner):** **not allowed without permission.** The Acceptable Use Policy (section 4) says "You may not use data mining, robots, screen scraping, or similar data gathering and extraction tools on this site, except with our express written consent". API use "will be subject to a separate set of terms available upon request". Section 1.3 also claims the compilation of content (including "data compilations") as Kitsu's exclusive property. So bulk collection needs written consent (legal@kitsu.app). The M3 plan's Kitsu import of a user's own list should also wait for those API terms.
  - **Larger Kaggle MAL dumps (2020, 2023):** fresher, but scraped against MAL's terms. Fine for a private measurement, risky to ship.

## Shikimori collector (session 8)

The owner wants a local dataset of many users' lists, so tuning is measured across thousands of users instead of guessed from one list. Shikimori is the source whose terms allow it (see above). `konomi collect-shikimori` (`lab/src/konomi/shikimori.py`, tests in `lab/tests/test_shikimori.py`; notes in the Shikimori collector learning in `.trail/learnings/`) is built to run overnight on the owner's Windows PC:
- **Requests:** samples user IDs 1..newest in a fixed random order (seed and newest ID stored at the first run), and fetches `GET /api/users/{id}/anime_rates?limit=5000&page=1`. The manga list is fetched only when the anime list isn't empty (empty accounts are common). A list longer than 5,000 comes back with one extra row (v1 returns `limit + 1` when there's more), and the collector then fetches the next page; before session 10 such lists were silently cut at 5,000.
- **v2 is ruled out (session 10):** `GET /api/v2/user_rates?user_id=` would return both lists in one compact request (about a third more users an hour), but **it ignores list privacy**. In Shikimori's source, v1's list endpoints call `authorize! :access_list, user` (`list_privacy_public?`), while v2's index builds `UserRate.where(user_id:)` and guests may `read` any UserRate. Two live private users gave empty v2 replies, most likely because their lists were empty. Don't switch to v2.
- **Limits:** 80 requests a minute by default (Shikimori allows 90), and the User-Agent is the app name (`konomi-moe`). The owner couldn't register an OAuth app (the confirmation code arrived after it expired), so it runs unregistered: the public endpoints need no account, and the name is still sent honestly. `--contact` adds a URL or email to the User-Agent; it's opt-in, because sending the owner's repo URL unasked was blocked as unsanctioned communication. After 15 refusals (403) in a row it stops with `Refused` and deletes those attempts so they're retried, because a 403 normally means a private list and a block would otherwise mark everyone private. Private lists are rarer than first thought: 2 of 81 random IDs on 2026-11-18 (the earlier "1 in 5" was a guess). It honours 429 `Retry-After`, backs off on 5xx, network errors and replies that aren't JSON (a maintenance page), and stops cleanly (resumable) on any other 4xx instead of crashing.
- **Storage:** `data/shikimori.sqlite`, one transaction per user, so it can resume. Users get anonymous numbers, IDs are kept only as salted hashes, and nicknames are never stored. Statuses and scores are stored as AniList's (POINT_100), plus progress, rewatches, `updated_at` and (since session 10) `created_at`, the date the title was added to the list. `created_at` is what a time-split evaluation needs; `updated_at` moves on every score edit or rewatch. `attempts.started` counts entries other than PLANNING, and `attempts.dated` marks users stored with dates.
- **What counts (session 10):** `--users` and `--min-entries` count users who *started* N titles. Planned titles don't count, so a list of 10 planned titles no longer counts as a useful user.
- **Upgrading older datasets (session 10):** a dataset collected before session 10 is upgraded on the next run (`_upgrade` adds the columns and counts `started` from what's stored). Its users are then fetched again first, because the sample order reaches them first, and keep their anonymous numbers. A list made private or deleted since is removed. The live status shows how many are left; at 80 a minute that's roughly 2,400 users an hour. `--status` works on old and new files and never writes.
- **Stopping:** no limit by default (`--users` is an optional cap). A live `rich` status shows users, stored, entries, IDs tried, requests, running time and users an hour. Q (`keys.StopKey`: `msvcrt` on Windows, cbreak plus `select` elsewhere, a no-op without a terminal) or the first Ctrl+C asks to stop, and `Collector.run(should_stop=…)` checks between users, so it exits after the current user. A second Ctrl+C exits at once. `run` returns stopped, target or exhausted. Progress uses running totals rather than counting rows after every user. Checked in a real pseudo-terminal against the live API: Q exited 2.5 s later and Ctrl+C 0.8 s later, cleanly, and the next run resumed with no half-saved users.
- **Rate:** the domain moved to **shikimori.io** (shikimori.one redirects). In two live smoke runs, 13 random IDs gave 3 users with 10+ entries, so expect roughly 500-1,000 useful users an hour. That counted planned titles and is a tiny sample, so trust the live rate. The target of 20,000 is several nights; the command shows its real rate and time left.
- **Checked live (session 10):** a capped run (2 users, 172 entries) stored `created_at` for every entry, and v1 accepted the `page` parameter. The data was deleted afterwards.
- **Next:** see "Plan for the Shikimori data" below.

## Plan for the Shikimori data (session 10)

The goal is to recommend titles the user **hasn't started** that they're most likely to enjoy, as accurately as possible. The dataset serves two purposes: measuring that goal across thousands of users, and training a model that learns from all of them rather than from one list. Review of the earlier plan, agreed with the owner:

**Why the current harness can't settle this.** `cross_validate` (`lab/src/konomi/evaluate.py`) hides some titles a user already finished or dropped, and checks that the liked ones rank higher. That's re-ranking titles the user chose to watch, which is a narrow task (every model lands near AUC 0.7). It can't see what other people's data is best at, finding titles the tag model never reaches, so the +0.012 AUC from the MAL experiment says little about it. Running the same test on 20k users would give tighter numbers on the wrong question, and the learning curve could look flat for that reason alone.

Steps, in order:
1. **Prepare.** Map MAL IDs to AniList: the offline database for anime, AniList `idMal` lookups for frequent manga. Title features: AniList details (tags, staff, relations, recommendation links) for frequent titles only, within AniList's terms (the owner approved this); the offline database's tags, year and relations for the remaining anime. Many users imported their MAL list, which gives hundreds of entries the same `created_at`; those entries carry no order, so keep them for training and leave them out of held-out sets.
2. **Split users, not titles.** Choose settings on tuning users (say 70%) and report only on the held-out test users. The current settings were picked and reported on the same owner's list, which flatters them.
3. **Test on the whole catalog, split in time.** For each test user with enough history (about 30+ started titles, 5+ of them after the cutoff), hold out the titles they started last and train on what they had added before.
   - **Candidates:** every title released before the cutoff, minus everything on their list then (planned included, as "Hide titles on my list" does by default). Also minus what the app hides: other versions of listed titles, sequels whose prequel isn't on the list, and adult titles.
   - **Sequels:** sequels of watched titles are easy hits that inflate whichever model wins, so score them separately as a "continue" list.
   - **Answer key:** positives are held-out titles they completed or scored at or above their own mean; negatives are held-out drops and low scores.
   - **Metrics:** recall@20 and NDCG@20, plus the share of the top 20 they later dropped. Average per user, with confidence intervals, broken down by list length (10–30, 30–100, 100+ started) and by type.
4. **Compare models on the same set of titles** (those with features and a vector; report coverage separately):
   - popularity among training users, and AniList's community score;
   - the current tag and staff ridge model;
   - item vectors (implicit SVD as in `lab/scripts/cf_experiment.py`), with the user's vector fitted by ridge regression instead of the weighted sum;
   - a hybrid with item vectors as extra ridge features;
   - a ranker trained on every title, untouched titles as weak negatives and drops or low scores as strong ones, with scores refining the order. This tests the target question: "would they start it and enjoy it" vs. "how would they rate it, given they watched it".
5. **Candidates.** The ranker can only order what reaches the pool. Measure what share of held-out liked titles each source reaches: the nearest titles to the user's vector (offline, shippable, no AniList calls) vs. AniList recommendation links of liked titles (from step 1's links). The app's live tag searches can only be approximated offline.
6. **Population model for short lists.** Short lists are the weak case: on the 46-title manga list the taste model still loses to the community score. A model trained across users (the hybrid, or population priors for tag weights) should help most there, and step 3's breakdown by list length shows whether it does.
7. **Learning curve** at 2k, 5k, 10k and 20k users on step 3's test. Keep collecting past 20k while it still climbs: titles with fewer than about 20 viewers get no vector, and those lesser-known titles are what a recommender most needs to reach. The MAL experiment used 341k users.
8. **Final check on AniList:** re-run the winner on the owner's real list.
9. **Before anything ships:** register the Shikimori OAuth app (shipping vectors from unregistered collection goes against the letter of its API rules), and check the vectors' size.

Watch out:
- The earlier finding that watch-based vectors beat score-based ones was about how *title vectors* were built. Both versions fitted the user to their scores and were graded within the list, so it doesn't show which target is right. On the full-coverage dataset it was split: watch-based won on AUC (0.717 vs 0.709), score-based at the top (hit@10 92–94% vs 89%). That dataset holds scored titles only, so "watch-based" there meant "scored at all". Step 4's last model tests the target question.
- Shikimori's users mostly speak Russian. Which titles go together should carry over; tuned label values (unscored completed = +1.0 and so on) may not. Step 8 guards against that.

## Suggested next steps

1. The Shikimori plan above, starting with the whole-catalog, time-split evaluation (the single-list `konomi evaluate` exists but only re-ranks titles already on the list).
2. Cleaner reasons (see observations above).
3. Variety in the top results (for example, a penalty for several picks that share a franchise or top tag).
4. Sequels of liked titles as a separate "continue" list, instead of mixing them in or filtering them out.
5. OAuth sign-in for private lists (only `ANILIST_TOKEN` is supported today).
6. A CLI command for adding to planning. ("Not interested" as a dislike and the format and year filters are built.)

## Do not

- Build a crawler for the whole AniList catalog, even a slow one. The API terms forbid mass collection, and the owner agreed to drop it. The offline database is the allowed full-catalog source, and only its top picks get fetched.
- Use real usernames or list data in tests, docs or learnings.
